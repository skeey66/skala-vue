# 모닥불 서비스 소개

모닥불은 비를 맞거나 바람이 세면 약해집니다. 캠핑도 마찬가지입니다.
비가 오거나 바람이 강한 날은 장비를 아무리 챙겨도 즐기기 어렵습니다.

여기서 착안해 그날의 날씨를 불이 얼마나 잘 타는지로 바꿔 100점으로 매긴 것이 모닥불 지수입니다.
오늘 어느 지역이 캠핑하기 좋은지, 그 날씨에는 어떤 방식이 맞는지, 조건에 맞는 야영장은 어디인지까지
캠퍼에게 알려 주는 서비스입니다.

## 과제1 — Weather Mockup

### 구현 내용

1. 목업 배열을 `v-for` 로 렌더링하고 `:key` 에 도시 id 를 지정
2. `v-if` / `v-else` 로 기온에 따라 다른 라벨을 표시
3. 검색창을 `v-model` 대신 `:value` 와 `@input` 의 조합으로 구현
4. 카드 안 버튼에 `@click.stop` 을 적용하고, 카드 클릭 시 `window.alert` 로 상세를 표시

### 최종 서비스 적용 여부

목업 배열은 과제6에서 API 응답으로 전부 교체했고, 좌표만 `data/cityList.js` 에 남았습니다.
3곳이던 목록은 전국 17개 시도가 되었습니다.

`@click.stop` 은 야영장 카드의 찜 버튼에 그대로 남아 있습니다. 버튼을 눌렀을 때 상세 화면이
함께 열리면 안 되기 때문입니다. `window.alert` 상세는 과제4에서 `router.push` 로 바뀌었습니다.

목업으로 목록을 구성하는 방식 자체는 커뮤니티(셰르파 동행, 장비 중고거래) 두 화면으로 확장했습니다.
글과 신청이 오가려면 서버가 필요한데 프런트엔드만 구현하는 과제이므로, 화면까지만 만들고
내용은 `data/communityMock.js` 에 두었습니다.

> 상태바("{도시}이 선택되었습니다")도 최종 실습본에서 제거했습니다.
> 카드를 눌렀다는 사실을 글로 알려주는 칸인데, 지금은 누른 지역이 지도에서
> 밝게 표시되고 타일에도 테두리가 생겨서 굳이 문장으로 다시 말할 필요가 없습니다.
> 클릭 처리와 `@click.stop` 은 그대로 남아 있습니다.

### 개인 추가·변경 내용

기본 제공은 서울·수원·부산 3곳에 `id` `name` `temp` `status` 네 개 필드였습니다.

1. 도시 7곳 추가 — 제주, 강릉, 대관령, 인천, 대구, 광주, 울릉도
2. 필드 6개 추가 — `feelsLike` `humidity` `wind` `rainProb` `dust` `updatedAt`
3. 강수확률 60% 이상이면 우산 라벨을 추가로 표시
4. 기준값을 상수로 분리 — `HOT_THRESHOLD`(25), `RAIN_THRESHOLD`(60). 카드 배지와 상단 요약이 같은 값을 참조
5. 상단 요약 추가 — "10개 · 평균 22.9°C · 25°C 이상 6곳 · 우산 3곳"

도시 값은 개수만 채우지 않고 조건 분기를 확인할 수 있도록 골랐습니다.
대관령 -2°C 는 음수 기온에서의 동작을, 인천 25°C 는 "25도 이상" 경계값이 어느 쪽으로
떨어지는지를 확인하기 위해 넣은 값입니다.

### 트러블 슈팅

한글 검색창에 `v-model` 을 적용했더니 "서울"을 입력하는 동안 "ㅅ", "서"가 들어오지 않고
글자가 완성된 뒤에야 반영되었습니다. 한글은 자모를 조합하는 중에도 input 이벤트가 발생하지만
`v-model` 은 조합이 끝난 글자만 전달하기 때문입니다. `:value` 와 `@input` 을 직접 연결해
해결했습니다.

## 과제2 — Weather Composition

### 구현 내용

1. `ref` 로 검색어와 정렬 기준을 반응형 상태로 선언
2. `computed` 로 검색 결과, 정렬된 목록, 평균 기온을 파생
3. `watch` 와 `watchEffect` 를 구분해 사용 — 관찰 대상이 분명하면 `watch`, 그렇지 않으면 `watchEffect`
4. `watch` 의 `onCleanup` 으로 이전 비동기 요청을 취소
5. 라이프사이클 훅의 실행 순서를 확인하고, DOM 이 필요한 작업을 `onMounted` 이후로 이동
6. watch 의 실행 시점을 화면에서 확인하기 위한 로그 패널 구현

### 최종 서비스 적용 여부

computed 체인은 지금도 화면의 뼈대입니다. 캠핑장 찾기는 전국 목록에서 사진이 있는 곳을 거르고,
검색어로 거르고, 조건으로 다시 거르는 과정이 모두 computed 로 이어집니다.

`watch` 는 주소와 화면 상태를 연결하는 데 사용합니다. 검색어가 바뀌면 `?q=` 를 갱신하고,
`?district=` 가 바뀌면 해당 시군구의 예보와 야영장을 다시 조회합니다.

`onMounted` 와 `onBeforeUnmount` 는 Leaflet, ResizeObserver, IntersectionObserver, 스크롤 잠금처럼
Vue 외부의 자원을 등록하고 해제하는 자리에 사용합니다.

> 반응형 로그 패널은 최종 실습본에서 제거했습니다.
> `watch` / `watchEffect` 가 언제 도는지 화면에서 확인하려고 만든 것인데,
> 캠핑 날씨를 보러 온 사람에게는 필요 없는 화면이라 뺐습니다.
> `console.log` 와 스토어 로그는 남아 있어 동작은 개발자 도구에서 확인할 수 있습니다.

로그만 출력하던 watcher 다섯 개도 함께 제거했고, 주소를 동기화하는 두 개는 남겼습니다.

### 개인 추가·변경 내용

1. 정렬 기준 `sortKey` 추가 — 기본순 / 기온 높은순 / 이름순
2. `visibleList` 추가 — 검색 결과에 정렬까지 적용하는 computed 체인
3. `averageTemp` 추가 — 화면에 보이는 도시의 평균 기온
4. `watch(searchQuery)` 에 `onCleanup` 을 적용해 이전 요청을 취소
5. 로그 패널 UI 구현

4번은 요구사항에 없는 항목입니다. 예시 화면 콘솔에 보이던 `started` / `completed` 로그가
어떤 동작인지 직접 확인하고 싶어 구현했습니다. 빠르게 입력하면 `started` 다음에 `cancelled` 가
이어지고, 마지막 입력만 `completed` 까지 도달합니다.

### 트러블 슈팅

캠핑장 조건 필터에서 지형·시설 칩을 눌러도 아무 반응이 없었고 오류도 발생하지 않았습니다.
`flip(terrains, item)` 처럼 ref 를 인자로 전달했는데, template 에서는 ref 가 자동으로 해제되어
함수가 받은 값은 ref 가 아니라 배열이었습니다. 그래서 함수 내부의 `.value` 대입이 원본에
반영되지 않았습니다. 어느 그룹인지를 문자열로 받아 함수 안에서 ref 를 선택하도록 수정했습니다.

## 과제3 — Weather Component

### 구현 내용

1. 한 파일에 있던 화면을 `WeatherParent`, `BaseDashboardCard`, `SearchBar`, `WeatherCard` 로 분리
2. 부모가 상태를 관리하고 `props` 로 전달, 자식은 `emits` 로 상위에 통지
3. `BaseDashboardCard` 는 내용을 알지 못하도록 `<slot>` 으로만 전달받게 구성
4. `<style scoped>` 로 컴포넌트별 스타일을 격리

### 최종 서비스 적용 여부

`WeatherParent` 만 `RegionsView` 로 이름이 바뀌었고 나머지 셋은 그대로 사용하고 있습니다.

`BaseDashboardCard` 는 현재 사이트 모든 패널의 공통 형태를 담당합니다. 직사각형, 상단의 얇은 선,
화면에 진입할 때 한 번 나타나는 연출까지 이 컴포넌트에 있으며, 여전히 내부에 어떤 내용이
들어오는지는 알지 못합니다.

컴포넌트는 네 개에서 열다섯 개가 되었습니다.

### 개인 추가·변경 내용

1. `BonfireGauge` 추가 — 지수를 모닥불 그림으로 표현하는 SVG. 점수 구간에 따라 불꽃 갈래와 불티 수가 달라짐
2. `CampSheet` 추가 — 야영장 상세 드로어. 캠핑장 찾기, 오늘의 추천, 찜, 지역 상세 네 화면이 공유
3. `RegionMap` / `CampMap` 추가 — Leaflet 지도. 시도 경계 색상 표현과 야영장 번호 마커
4. `PageHero` 추가 — 화면 상단의 전면 사진 배너
5. `BaseDashboardCard` 에 IntersectionObserver 기반 등장 연출 추가

### 트러블 슈팅

1. `CampSheet` 를 세 화면에 적용했는데 드로어가 오류 없이 열리지 않았습니다. `import` 누락이
   원인이었지만 eslint 와 빌드 모두 통과했습니다. eslint 는 template 안의 미등록 컴포넌트를
   검사하지 못합니다
2. `BonfireGauge` 를 한 화면에 열일곱 개 배치했더니 전부 마지막 컴포넌트의 색으로 표시되었습니다.
   SVG 그라디언트 `id` 가 모두 같아 문서 안에서 충돌한 것이므로 `useId()` 로 구분했습니다
3. 주간 그래프의 폭이 갱신되지 않았습니다. `:key` 로 지역을 바꾸면 해당 요소가 새로 생성되는데,
   ResizeObserver 를 `onMounted` 에서 한 번만 등록해 이미 제거된 요소를 관찰하고 있었습니다

## 과제4 — Weather Router

### 구현 내용

1. Router 를 도입하고 `App.vue` 에 `<RouterView />` 와 내비게이션 바를 배치
2. `/weather/:cityId` 동적 경로를 `route.params` 로 받아 상세 화면을 렌더링
3. `/:pathMatch(.*)*` Catch-all 을 마지막에 두어 404 를 처리
4. 모든 라우트를 `() => import()` 로 감싸 화면별 청크로 분리
5. 상세 화면 이동을 `window.alert` 에서 `router.push()` 로 변경

### 최종 서비스 적용 여부

라우트는 열두 개가 되었습니다. 이 단계에서 가장 크게 남은 것은 상태를 주소에 담는 방식입니다.
보기 모드(`?view=`), 야영장 종류(`?type=`), 시군구(`?district=`), 지역(`?region=`), 검색어(`?q=`)가
모두 주소에 들어갑니다. 덕분에 링크를 그대로 공유할 수 있고 뒤로 가기가 예상대로 동작합니다.

화면을 통합하면서 없어진 주소는 리다이렉트로 남겼습니다. `/ranking` 은 `/regions?view=rank` 로 연결됩니다.

### 개인 추가·변경 내용

1. `/ranking` 화면 추가 — 이후 날씨 화면의 보기 모드로 통합
2. 검색어를 `?q=` 에 유지해 상세 화면에 갔다 돌아와도 상태가 남도록 처리
3. 404 화면에 `route.fullPath` 를 함께 표시
4. 존재하지 않는 도시 코드(`/weather/city_99`)를 상세 화면 안에서 안내

### 트러블 슈팅

첫 화면에서 스크롤을 가로채는 처리를 추가했더니 다른 화면으로 이동한 뒤에도 스크롤이 잠긴 채
남았습니다. SPA 는 페이지를 새로 불러오지 않으므로 `onBeforeUnmount` 에서 직접 해제해야 합니다.

## 과제5 — Weather Store

### 구현 내용

1. Pinia 스토어를 `state` / `getters` / `actions` 로 구성
2. 단위 상태를 `configStore` 에 두고 `UnitToggler` 를 내비게이션 바에 배치
3. 인자를 받는 getter 구현 — `isFavorite(id)`
4. 단위 변환을 `useTemperature` composable 로 분리
5. 관심 목록을 `localStorage` 에 저장

### 최종 서비스 적용 여부

`configStore` 는 실습에서 만든 형태 그대로 사용하고 있습니다.

`weatherStore` 는 서비스의 중심이 되었습니다. 17개 지역의 응답을 모아 10분간 캐시하고,
지역별 야영장과 주간 예보도 이곳에서 관리합니다. 화면을 이동해도 다시 조회하지 않습니다.

`favoriteStore` 는 관심 지역에서 야영장 찜으로 바꿨습니다. 실제로는 지역이 아니라 가고 싶은
캠핑장을 담아 두었다가 예약하기 때문입니다. 야영장 정보는 API 에서 오므로 id 만 저장하면
찜 화면을 열 때마다 전국 목록을 다시 받아야 해서, 화면에 필요한 만큼만 함께 저장합니다.

`useTemperature` 도 그대로 남았습니다. 원본 값은 항상 섭씨로 두고 화면에 표시할 때만 변환합니다.
25도 이상 같은 판정은 원본 값으로 해야 단위를 바꿔도 결과가 달라지지 않습니다.

### 개인 추가·변경 내용

1. `favoriteStore` 추가 — getter `count` / `isFavorite` / `recent`, action `toggle` / `remove` / `clear`
2. `configStore` 에 `unitLabel`, `isFahrenheit` getter 와 `setUnit` action 추가
3. 찜을 세 곳에 연동 — 카드의 찜 버튼, 상세 드로어의 버튼, 내비게이션 바의 개수 배지

### 트러블 슈팅

내비게이션 바에는 "찜 3"이 표시되는데 찜 화면은 비어 있었습니다. `localStorage` 에 실습 초반의
이전 id(`city_02`)가 남아 있었고, 그 사이 지역 id 체계가 `sido_11` 로 바뀐 상태였습니다.
배지는 개수만 세고 화면은 해당 지역을 찾지 못한 것입니다. 데이터를 불러올 때 존재하지 않는
id 를 제외하도록 수정했습니다.

## 과제6 — Weather Axios

### 구현 내용

1. `axios.create` 로 baseURL, timeout, 공통 params 를 한곳에 정의
2. 목업을 제거하고 OpenWeatherMap 의 현재 날씨와 대기 오염을 실제로 연동
3. `Promise.all` 로 여러 도시를 동시에 조회하고, 일부 실패를 허용해야 하는 곳은 `allSettled` 로 처리
4. 응답 인터셉터로 오류 처리와 재시도를 한곳에 집중
5. CORS 로 차단되는 공공데이터포털은 개발 서버 프록시로 우회

### 최종 서비스 적용 여부

이 단계에서 목업이 빠지면서 실제 캠핑 서비스가 되었습니다. 사용하는 API 는 세 곳입니다.

- OpenWeatherMap — 현재 날씨, 3시간 예보와 강수확률, 대기 오염, 지오코딩
- Open-Meteo — 자외선, 밤 최저기온, 해발고도, 시군구 250곳 예보
- 고캠핑 — 전국 야영장 목록, 반경 야영장, 야영장 사진

모닥불 지수는 이 값들을 100점으로 환산한 것입니다. 배점은 비 30, 바람 25, 밤 기온 25,
공기 12, 하늘 8이며 등급은 활활 / 타닥타닥 / 가물가물 / 연기만 네 단계입니다.

바람은 평균이 아니라 순간 최대풍속을 기준으로 합니다. 밤 기온은 4~14도가 최적이고 26도를
넘으면 2점만 부여합니다. 낮이 아니라 밤 기온을 보는 것은 캠핑이 그 자리에서 잠을 자기 때문입니다.

인터셉터는 `api/retry.js` 하나로 모아 세 API 가 공유합니다.

### 개인 추가·변경 내용

1. 캠핑 주제로 전환 — 밤 최저기온을 중심에 두고 지수를 불의 표현으로 옮김
2. `useBonfireScore` 추가 — 지수, 등급, 오늘에 맞는 캠핑 방식, 침낭 등급, 바람 판정을 한곳에 정리
3. 요소별 점수 표시 — 합계만으로는 근거를 알 수 없어 비 30/30, 기온 6/25 처럼 항목별로 표시
4. Open-Meteo 좌표 묶음 호출 — 좌표를 콤마로 연결해 17개 지역을 1회 호출, 시군구 250곳도 1회 호출
5. 5일 야간 예보 — `/forecast` 40구간에서 18시부터 다음 날 06시까지를 하루로 집계
6. 시도에서 시군구로 내려가는 드릴다운 구현
7. 전국 야영장 3,096곳을 한 번에 받아 브라우저에서 필터링 (사진이 있는 곳 2,333곳)
8. 조건 필터 — 지역, 지형, 시설, 화로대, 반려동물 동반
9. 한글 부분 검색 — "울ㅅ"으로 울산이 검색되고, "ㅈㅈ"처럼 자음만 입력하면 초성 검색으로 동작
10. 지오코딩 연동 — 목록에 없는 지역도 좌표를 받아 목록에 추가

### 트러블 슈팅

1. 공공데이터포털은 CORS 헤더를 제공하지 않아 브라우저에서 직접 호출할 수 없어 프록시를
   두었습니다. 인증키도 Encoding 값을 사용하면 axios 가 한 번 더 인코딩해 인증에 실패하므로
   Decoding 값을 사용합니다
2. Open-Meteo 와 OpenWeatherMap 이 모두 `sunrise` 를 제공하는데 형식이 달라(ISO 문자열과 초 단위)
   객체를 병합할 때 값이 덮어써졌습니다. 한 곳에서만 받도록 정리했습니다
3. 밤 구간을 집계할 때 날짜 키를 `toISOString()` 으로 만들면 UTC 로 변환되면서 한국 시간
   저녁 18~23시가 전날로 분류됩니다. 지역 시각의 연·월·일을 직접 조합해야 합니다
4. 시군구 목록에 "바람 17.3"이 표시되어 확인해 보니 Open-Meteo 는 풍속을 km/h 로 제공합니다.
   지수의 바람 기준은 m/s 이므로 3.6배로 읽혀 바람 25점이 전부 0점이 되고 있었습니다.
   요청에 `wind_speed_unit: 'ms'` 를 추가해 단위를 맞췄습니다
5. 고캠핑의 `searchList` 는 야영장 이름만 검색합니다. "강원"을 입력하면 이름에 강원이 포함된
   두 곳만 나옵니다. 지역 기준으로 찾으려면 전체 목록이 필요해 `basedList` 로 한 번 받아 두고
   브라우저에서 필터링합니다
6. 시군구를 확인하던 중 429 오류가 발생했습니다. 고캠핑의 일일 요청 한도 초과였고, 한도는
   오퍼레이션별로 따로 적용됩니다. 좌표별 캐시와 320ms 디바운스를 적용하고, 429 를 일시적인
   집중과 일일 한도 소진으로 구분해 전자의 경우만 재시도하도록 수정했습니다

## 과제7 — Weather UI Library

### 구현 내용

1. UI 라이브러리를 비교한 뒤 Naive UI 선택
2. `NConfigProvider` 로 앱을 감싸고 다크 테마 적용
3. `theme.js` 에 테마 오버라이드를 작성해 프로젝트 팔레트를 주입
4. 목록 자리를 Skeleton, 결과 없음을 Empty, 오류를 Alert 로 대체
5. 상세 화면을 Drawer 로 열고 사진을 Carousel 로 표시

### 최종 서비스 적용 여부

동작이 필요한 곳에만 사용하고, 화면의 인상을 결정하는 카드·눈금·배너·지수 게이지는 직접 만든
컴포넌트를 유지했습니다. 현재 사용 중인 것은 Drawer, Carousel, Image, Skeleton, Tag, Select,
Empty, Alert, Message, Tooltip, Button, BackTop, ConfigProvider 이며 `theme.js` 도 그대로입니다.

### 개인 추가·변경 내용

1. 라이브러리를 전면 도입하지 않았습니다. 기본 컴포넌트를 그대로 사용하면 서비스가 라이브러리
   데모처럼 보이기 때문입니다
2. `theme.js` 오버라이드로 캠핑 팔레트를 주입해 직접 만든 부분과 색이 어긋나지 않도록 했습니다
3. 야영장 사진을 Carousel 로 최대 8장까지 표시
4. Skeleton 을 목록·예보·야영장 세 곳에 각각 형태를 맞춰 적용

### 트러블 슈팅

1. `NCarousel` 은 자체 높이를 갖지 않습니다. 드로어 안에 넣었더니 남은 세로 공간을 모두 차지해
   아래 내용이 화면 밖으로 밀려났습니다. 높이를 직접 지정해야 합니다
2. keyframe 안에서는 `var()` 로 지정한 `width` 가 해석되지 않아 배점 막대가 계속 0px 이었습니다.
   길이는 요소에 고정하고 변화하는 값만 `transform: scaleX()` 로 처리했습니다
3. `mix-blend-mode: screen` 을 안쪽 요소에 적용했더니 부모가 `z-index` 로 만든 쌓임 맥락에
   갇혀 의도한 대로 합성되지 않았습니다
4. 전면 배너를 만들면서 `overflow-x: clip` 을 본문에 적용했더니 배너가 잘렸습니다.
   `html` 에 적용해야 합니다

## 과제8 — Weather Deployment

### 구현 내용

1. ESLint 와 oxlint 를 함께 적용하고 규칙 위반을 정리
2. Prettier 로 서식 통일
3. API 키를 `.env` 로 분리하고 `.gitignore` 에 등록
4. `vite build` 로 정적 파일을 생성하고 화면별 청크 분리를 확인

### 최종 서비스 적용 여부

Vercel 에 배포했습니다. `npx eslint .` 는 오류 0개, `npx prettier --check src/` 는 전부 통과합니다.

배포하면서 가장 크게 바꾼 것은 인증키 처리입니다. `VITE_` 접두사를 붙이면 값이 번들에 포함되어
개발자 도구에서 그대로 확인할 수 있고, 저장소가 공개 상태라 더 문제가 됩니다. 프런트엔드만으로는
막을 수 없어 서버를 한 단계 두었습니다.

`api/` 에 서버리스 함수를 두고 브라우저는 `/api/owm/...` 같은 동일 출처 주소만 알도록 했습니다.
인증키는 서버 환경변수에만 존재하며 함수가 이를 붙여 원본 API 로 전달합니다. 공공데이터포털의
CORS 문제도 같은 함수가 함께 해결합니다.

`createWebHistory` 를 사용하므로 `/camps` 로 바로 접속하면 404 가 발생합니다.
`vercel.json` 에 SPA fallback 을 설정했습니다.

### 개인 추가·변경 내용

1. 인증키를 브라우저에서 제거 — 서버리스 함수와 이에 맞춘 개발 서버 프록시를 구성했습니다.
   빌드 산출물과 실제 네트워크 요청 어디에도 키가 남지 않는 것을 확인했습니다
2. 인증키가 필요 없는 Open-Meteo 도 동일 출처를 거치도록 했습니다. 외부 도메인을 브라우저가
   직접 호출하면 해당 도메인이 차단된 네트워크에서 화면 전체가 동작하지 않습니다
3. `index.html` 정리 — 스캐폴딩 기본값이라 탭 제목이 "Vite App" 으로 남아 있었습니다
4. 미사용 코드 정리 — 호출되지 않는 함수와 스토어 액션, 어떤 template 에서도 쓰이지 않는
   CSS 클래스와 토큰을 제거했습니다

### 트러블 슈팅

1. 배포 후 날씨와 야영장이 모두 표시되지 않았습니다. 함수를 `api/owm/[...path].js` 캐치올
   형태로 두었는데 Vercel 이 이를 한 단계 동적 경로로만 인식했습니다. `/api/gocamping/basedList`
   는 동작하고 `/api/owm/data/2.5/weather` 는 404 였습니다. 함수를 단일 파일로 두고 원본 경로는
   `vercel.json` 의 rewrite 가 `?path=` 로 전달하도록 변경했습니다
2. 다른 컴퓨터에서 접속하면 지수가 전혀 표시되지 않았습니다. Open-Meteo 만 브라우저가 외부
   도메인을 직접 호출하고 있었고, `weatherStore.load` 가 `Promise.all` 이라 그 한 곳이
   거부되면 정상적으로 받아온 관측값까지 함께 버려졌습니다. 예보도 프록시를 거치게 하고,
   실패는 `catch` 로 처리해 관측값만이라도 표시하도록 수정했습니다
3. `.env` 를 확인하려고 셸에서 `set -a; . ./.env` 로 읽었다가 PATH 가 초기화되어 `curl` 을
   사용할 수 없게 되었습니다. `.env` 안에 셸이 해석할 수 있는 값이 있으면 환경 변수 전체가
   덮어써집니다
